# Ratatoskr Workspace

`ratatoskr-workspace` is the coordination repository for Ratatoskr: a self-hosted, multi-repository platform for capturing, extracting, analysing, searching, and backing up personal knowledge from the web, GitHub, social networks, Telegram, ChatGPT, and Claude.

> **Status:** reproducible snapshot slice implemented. Sixteen public child repositories are pinned
> by gitlinks; `workspace.toml`, `workspace.lock`, the Rust snapshot harness, and hosted snapshot CI
> are executable. Task-worktree, general integration-profile, PR, release, and MCP orchestration
> remain later milestones.

> [!IMPORTANT]
> **Ratatoskr is in development.** No database holds data that has to survive a schema change.
> While this status holds, these two rules replace what the documents below plan:
>
> - the API and the database keep their first version. There is no `v2` and no later major
>   version.
> - the database has no migrations. One schema definition exists, and a schema change edits it in
>   place.
>
> Only the repository owner changes this status.

## Role in Ratatoskr

Ratatoskr is intentionally split into independent repositories and bounded contexts. This repository gives that distributed codebase the useful properties of a monorepo without merging component histories or release lifecycles.

It is responsible for:

- pinning a known-compatible commit of every Ratatoskr repository;
- describing repository dependencies, commands, profiles, and contract relationships;
- creating isolated task-specific Git worktrees;
- coordinating cross-repository changesets and pull requests;
- holding the OpenSpec store the whole fleet plans against;
- running system-level integration and restore tests;
- generating shared Claude Code and Codex configuration;
- producing reproducible deployment and release snapshots.

It does **not** own runtime domain data or implement product services.

## Repository topology

The workspace is a Git superproject whose child repositories are mounted as read-only submodules under `repos/`:

```text
repos/
├── contracts/
├── platform/
├── extractor/
├── knowledge/
├── github/
├── vault/
├── integrations/
│   └── telegram/
├── social/
│   ├── x/
│   ├── instagram/
│   └── threads/
├── ai-archive/
│   ├── chatgpt/
│   └── claude/
└── clients/
    ├── web/
    ├── mobile/
    ├── browser-extension/
    └── export-agent/
```

The legacy `ratatoskr` backend and its web client are retired. They are kept only as local
read-only archives, they have no Git remote, and they are not pinned in this workspace. The
`ratatoskr-web` repository name is reused by the new web client and shares no history with the
retired one.

Three files jointly define workspace state:

1. **Git submodule pointers** pin exact compatible commits.
2. **`workspace.toml`** describes semantic metadata, dependency edges, commands, and deployment profiles.
3. **`workspace.lock`** is a generated snapshot containing commit SHAs, contract digests, schema versions, and build metadata.

`workspace.lock` is generated by the harness and must not be edited manually.

## Clone and verify the snapshot

```bash
git clone --recurse-submodules https://github.com/po4yka/ratatoskr-workspace.git
cd ratatoskr-workspace
git submodule update --init --recursive
./ws manifest check
./ws lock check
./ws status
./ws doctor
```

`manifest check`, `lock check`, `status`, and `doctor` never fetch, check out, reset, clean, or
repair a child. `status` reports drift and dirt without failing solely for those observations;
`doctor` is the strict gate. Regenerate derived evidence only through:

```bash
./ws lock generate --output workspace.lock
```

Rollback is a normal revert of the coherent workspace commit. Never repair a dirty baseline by
resetting it; preserve the work and investigate it outside `repos/`.

## Worktree-based agent workflow

Directories under `repos/` are pinned baselines and are never edited directly. For each changeset, the harness creates independent Git worktrees:

```text
.workspaces/RTK-142/
├── task.yaml
├── context.md
├── results/
└── repos/
    ├── contracts/
    ├── x/
    ├── knowledge/
    └── web/
```

Core rules:

- one writer agent per repository within a changeset;
- agents write only inside their assigned worktree;
- repository-local `AGENTS.md` and `CLAUDE.md` remain authoritative for implementation details;
- the workspace harness owns branches, validation, commits, and PR coordination;
- contract changes follow an expand/migrate/contract rollout rather than synchronized breaking releases.

Claude Code and Codex are interchangeable execution backends behind a common runner contract. Agent-native subagents may help with local analysis, but repository topology and cross-repository orchestration remain deterministic harness responsibilities.

## Cross-repository changesets

Git cannot provide a single atomic commit across multiple repositories. Ratatoskr models the logical unit explicitly in `changesets/<id>.yaml`.

A changeset records:

- goal and scope;
- affected repositories and their roles;
- dependency and merge order;
- compatibility strategy;
- required verification;
- rollout and rollback order;
- linked pull requests and resulting merge SHAs.

The workspace `main` branch represents the latest fully verified compatible system snapshot. Individual child repositories may move ahead independently; `ws drift` reports the difference. Workspace tags identify reproducible release and deployment snapshots.

## Integration environment

The profiles below are **developer-machine artifacts**, sized for a workstation and meant to be run
in parallel per task. They are not the deployment. Ratatoskr deploys to one Raspberry Pi 5 supervised
by systemd, described in [`docs/DEPLOYMENT_TARGET.md`](docs/DEPLOYMENT_TARGET.md) — a single,
non-parallel arrangement with its own storage layout, port allocations and resource budget. A
service's Compose entry here says nothing about whether it can run there, which is the confusion
worth naming: a dependency that exists only in a Compose profile is a dependency that is installed
nowhere.

One narrow profile is implemented now:

- `integration/compose/web-operational.yaml` builds published Platform and Web revisions from
  explicit checkout paths, seeds bounded synthetic owner/member data, and verifies healthy,
  degraded, and recovered status through public HTTP;
- `integration/run-web-operational.sh` validates exact revisions, assigns ephemeral loopback ports,
  runs the API and Playwright smoke, and removes only its Compose project; and
- [`integration/README.md`](integration/README.md) gives the exact inputs and command.

This is not the planned general integration harness. The broader target remains:

```text
integration/
├── compose/
│   ├── base.yaml
│   ├── core.yaml
│   ├── git.yaml
│   ├── social.yaml
│   ├── ai-archive.yaml
│   └── full.yaml
├── fixtures/
└── tests/
```

Each task receives isolated PostgreSQL databases or schema namespaces, NATS streams, BlobStore prefixes, ports, and volumes so multiple changesets can be validated concurrently.

Planned profiles:

- `core`: platform, extractor, knowledge, PostgreSQL, NATS, and BlobStore;
- `git`: GitHub catalog and Git Vault;
- `social`: X, Instagram, and Threads;
- `telegram`: Telegram bot and Mini App integration;
- `ai-archive`: ChatGPT and Claude archive services;
- `full`: all supported services and clients.

## Non-negotiable invariants

1. Baseline submodules are read-only.
2. Every cross-repository change has a changeset ID.
3. Every child repository builds and tests independently outside this workspace.
4. Production dependencies never rely on committed relative paths between repositories.
5. Workspace `main` always identifies a verified compatible snapshot.
6. Secrets never enter manifests, task context, agent prompts, logs, or traces.
7. Agents do not push, merge, or rewrite history outside the harness workflow.
8. System-level validation uses the exact task worktrees proposed for the change.

The first domain loop now exists in source: Platform publishes
`cmd.content.capture.requested.v1`, Extractor consumes it durably and reports the terminal operation
outcome, and Platform projects that report without discarding its structured detail. Knowledge can
analyse Document IR through its library pipeline, but it is not connected to that bus flow yet.

The deployment target remains frozen until the workspace can pin compatible commits and validate
them through an integration profile. `docs/DEPLOYMENT_TARGET.md` describes the machine as a
performance budget for the code being written now — four Cortex-A76 cores, 15 GiB, 16 KiB pages,
one NVMe — and not as an environment anyone operates.

The workspace now pins child commits and verifies manifest/gitmodule/gitlink/lock agreement. The
existing task-specific integration profiles remain separate evidence: snapshot consistency does not
claim a live deployment, provider session, or composed runtime is healthy.
